# Assumptions and limitations

- The public default is 168 hourly timesteps. `configs/annual.yaml` (8,760 hours) now has a real recorded run against real 2023 ERA5 wind — see `docs/reproducibility.md`'s 2026-09-01 section — but it is not the default config, and its wind-only/grid-only-cumulative variants are genuinely infeasible, not merely unrun.
- Wind and market arrays in demonstrations are synthetic and use fixed seeds.
- The pipeline relation is a screening approximation, not a transient pressure-network design model.
- Electrolyser efficiency is simplified and the optimiser uses a linear hydrogen coefficient.
- No electricity-network power flow (AC/DC power flow, voltage/thermal limits), startup duration, reserve market, stochastic uncertainty, or project finance model is included. Hydrogen storage and grid import/export are now implemented (Phase A1/A2) but are opt-in and off by default — see below.
- Configured live-data source names do not by themselves prove that live data were downloaded or consumed — `data/era5.py` implements and unit-tests a real CDS fetch/load/provenance path (see `docs/data_provenance.md`); a full year of real 2023 ERA5 wind has been fetched and run (Phase C1-C5 complete). ENTSO-E remains configured-but-not-implemented (Phase A3, deferred; see below).
- Hub-height wind speed for real ERA5 data is corrected from the 100m components using a power-law (default, offshore shear exponent 0.11) or log-law (open-sea roughness length 0.0002 m) shear model — both are approximations of the true boundary-layer profile at the specific site and date, not a site-specific measured shear profile.
- The turbine power curve defaults to a cubic approximation between cut-in and rated; a tabulated manufacturer curve can now be substituted via `wind_turbine.power_curve_csv`, but no such table is checked in yet, so the default remains the cubic approximation.
- Wake loss, electrical loss, and availability factors (`wind_turbine.wake_loss_fraction`, `electrical_loss_fraction`, `unavailability_fraction` in `config.yaml`) are named, sourced literature/benchmark values, not site-specific measurements.
- The ERA5 capacity-factor sanity check against published North Sea figures (Phase C4) and the 8,760-hour annual run (Phase C5) are both done — see `docs/validation.md` and `docs/reproducibility.md`. The resulting capacity factor (0.397) is a plausibility check against the broader published range (0.23-0.52), not validation of this model's specific loss-factor values or power curve.
- Hydrogen storage's fractional hourly loss (`hydrogen_storage.loss_fraction_per_hour`, default 0.0001, i.e. ~0.24%/day) assumes compressed gaseous storage (matches this repo's 30 bar pipeline outlet pressure), not cryogenic liquid H2 (which has a materially higher boil-off rate, ~0.1-1%/day) — it is a plausible order-of-magnitude assumption, not a sourced figure for any specific storage vessel.
- Hydrogen storage capacity/charge/discharge rates (`hydrogen_storage.*_kg` / `*_kg_h` in `config.yaml`) are sized for a smoothing buffer (~10h of average demand) by construction, not from a project-specific storage design.
- Grid connection capacity (`grid.connection_capacity_mw`, default 50 MW) is an illustrative partial-grid-connection figure, not a sourced interconnection study.
- Exported power is **not** credited as avoided grid emissions in the emissions objective — see `docs/formulation.md`'s Phase A2 section for why (marginal vs. average grid carbon intensity is genuinely contested; crediting it would need a sourced factor this repo doesn't have).
- The grid model has no binary preventing simultaneous import and export at the same hour; with a single price applying to both directions, this is cost-neutral and does not change aggregate results, but individual `g_imp[t]`/`g_exp[t]` values can be non-unique in a degenerate solution — see `docs/formulation.md`.
- Data reconciliation (`optimization/reconciliation.py`) operates on synthetic measurements and demonstrates the WLS + chi-square(1) method, not validation against plant instrumentation. It deliberately does not report a "likely culprit" sensor: with one balance equation across four sensors, the faulty sensor is not statistically identifiable from a single snapshot — see `docs/reconciliation.md`.
- ENTSO-E day-ahead prices (Phase A3): `data/entsoe.py` implements and unit-tests a real fetch/provenance path (same discipline as ERA5), but no live fetch has been run (needs a separate `ENTSOE_API_KEY`, not yet configured) and `pynexus solve` is not wired to consume it yet. `economics.electricity_price_source: "entso_e"` remains configured-but-not-executed. `pynexus solve --wind-csv` pairs real ERA5 wind with synthetic prices as an interim hybrid (see `docs/data_provenance.md`).
- Electrolyser waste heat (`electrolyzer.recoverable_heat_fraction`, default 0.5) uses the SAME linearised efficiency the dispatch model's hydrogen output already assumes (fixed at the 80%-load point), not the full nonlinear load-dependent curve in `components/electrolyzer.py` — using a different one would violate the electrolyser's own energy balance within the MILP. The 0.5 recoverable fraction is a stated range assumption (PEM coolant is 50-80°C, suits low-temperature use only), not a sourced figure for a specific stack.
- Heat storage/boiler sizing (`heat_storage.*`, `boiler.*` in `config.yaml`) and both value parameters (`economics.hydrogen_value_per_kg`, `economics.heat_value_per_mwh`) are illustrative, not sourced offtake contracts or a project-specific district-heating study.
- The coupled objective's hydrogen/heat value terms have **no measurable effect on electrolyser dispatch** at the configured `DEMAND_PENALTY` (1000 EUR/kg) — that penalty structurally dominates any economically plausible value signal. This is a real, tested finding (`docs/results.md`), not a limitation of the value terms' wiring (`test_coupled_objective_independently_reconstructed` confirms they are correctly counted) — it means the demand-slack penalty and the value terms are, as currently configured, answering different questions ("never miss demand" vs. "value what's delivered") and the former wins by construction.
- Heat storage and hydrogen storage share the same real limitation: with zero waste-heat/hydrogen production and any nonzero standing loss, requiring the store to hold at or above its initial level is genuinely infeasible (the store can only leak, never charge) — not a solver or model bug; see the corresponding tests in `tests/test_dispatch_heat.py` / `tests/test_dispatch_storage_grid.py`.
- Against real 2023 wind, `config.yaml`'s hydrogen demand (50 t/day) cannot be fully met by this system as configured, at any grid connection size up to the electrolyser's own 100 MW rating — even the best recorded annual run (grid + storage, soft hourly demand) leaves ~16% of annual demand unmet. This is a genuine capacity/demand sizing mismatch in the illustrative configuration, not a bug; see `docs/reproducibility.md`'s 2026-09-01 section for the numbers.
